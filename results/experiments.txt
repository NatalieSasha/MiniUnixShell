--- 4. Interpretation ---------------------------------------------
The trace shows the following sequence:
  * the shell process (pid of the traced program) starts and reads
    the command line;
  * a clone(2) (the Linux implementation of fork(2)) creates a child;
  * the child calls execve(2) to replace its program image with
    /bin/echo;
  * the child terminates with exit_group(2);
  * the parent calls wait4(2) (the Linux implementation of
    waitpid(2)) and collects the exit status.

Note: the exact sequence of library calls is implementation
dependent.  glibc implements fork(2) with clone(2) and waitpid(2)
with wait4(2); the POSIX names fork(2) and waitpid(2) are the
portable interface that the source code in src/process.c and
src/pipeline.c uses.

--- Process table during a background job ---------------------------
The shell prints the job number and the process id of the job:
    [1] 133

Interpretation:
  * The foreground run blocks for the whole duration of 'sleep'.
    The shell called fork(2), then waitpid(2); waitpid(2) does not
    return until the child has terminated, so the shell cannot read
    the next command line before that.
  * The background run returns immediately.  The shell called
    fork(2) but did not call waitpid(2) for that child; it recorded
    the process id in its job table and returned to the prompt.
  * The child is not orphaned: it is still a child of the shell.
    It becomes a zombie when it terminates and is reaped by the
    waitpid(-1, WNOHANG) call in process_reap_children().

--- 4. Interpretation ---------------------------------------------
  * The shell calls open(2) (glibc: openat(2) with AT_FDCWD) for the
    redirection target.  The mode argument is 0666; the kernel masks
    it with the current umask.
  * dup2(2) installs the new descriptor on position 0 or 1.  dup2(2)
    closes the target descriptor atomically, so there is no window in
    which the descriptor is invalid.
  * close(2) releases the temporary descriptor that open(2) returned.
  * The library function open(2) and the system call openat(2) are
    not the same thing: glibc implements open(2) as a wrapper around
    the openat(2) system call, and that is why openat(2) appears in
    the trace.

--- 3. Throughput of the pipe --------------------------------------
    200000
    elapsed: 112 ms for 200000 lines

Interpretation:
  * Each '|' makes the shell call pipe(2) (glibc uses pipe2(2) with
    O_CLOEXEC).  The read end becomes the standard input of the
    following stage, the write end becomes the standard output of the
    preceding stage; both are installed with dup2(2).
  * Every descriptor that is not needed by a stage is closed in that
    stage.  If a stage kept the write end of a pipe open, the reader
    would never see end-of-file and the pipeline would block
    forever.
  * All stages are forked before the shell waits for any of them, so
    the consumer starts running while the producer is still alive.

  result: no descriptor was leaked.
  the descriptors that are currently open:
    total 0
    lr-x------ 1 root root 64 Oct 21 18:05 0 -> /tmp/tmp.ozkNsOShDk/ctl
    l-wx------ 1 root root 64 Oct 21 18:05 1 -> /tmp/tmp.ozkNsOShDk/out.txt
    l-wx------ 1 root root 64 Oct 21 18:05 2 -> /tmp/tmp.ozkNsOShDk/out.txt

Interpretation:
  * A child that terminates stays in the process table as a zombie
    until its parent collects its exit status with waitpid(2).  The
    shell collects it in process_reap_children(), which calls
    waitpid(-1, WNOHANG) in a loop.
  * The reaping is deliberately *not* done inside the SIGCHLD handler:
    a signal handler may only use async-signal-safe functions, and
    printf(3) is not one of them.  The handler only sets a flag and
    the actual work happens in the normal control flow of the
    interpreter loop.
  * Every descriptor that the shell opens for a redirection is closed
    again, and the pipe descriptors of a pipeline are closed in both
    the parent and the child.
